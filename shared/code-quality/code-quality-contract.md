# 代码质量与注释契约

目标是在不扩大任务范围的前提下，让本次新增或修改的代码容易理解、可靠修改并能承受已经明确的变化。它约束当前任务 Diff，不要求顺带整理历史代码。

## 始终适用

- 命名表达业务意图和单位；`Manager`、`Helper`、`Utils`、`data`、`temp` 等泛化名称只有在职责确实稳定且清楚时使用。
- 函数、类型和组件保持单一清晰职责。优先使用早返回和明确状态减少嵌套；只有抽取后能降低认知负担或形成真实复用时才拆分。
- UI、业务状态、数据访问和平台副作用沿用项目现有边界；新增依赖只能指向更稳定的层，不让展示层直接承担网络、数据库或系统能力编排。
- 加载、空值、失败、取消、重复触发和生命周期恢复必须在相关路径显式处理；不得用默认值或吞错掩盖未定义行为。
- 扩展点必须对应已经存在或已确认的变化轴。不要为假想需求新增单实现接口、工厂、包装层、配置系统或第三方依赖。
- 公共接口、持久化结构、路由参数和跨模块模型的兼容性优先于内部整洁；需要破坏性变更时先登记影响和迁移方式。
- 复用项目已有术语、模式和工具。重复少量简单代码与引入错误抽象冲突时，选择更容易理解和删除的方案。

## 中文注释规则（本次新增/改动的自有代码）

- 每个自有函数/方法有中文说明：用途，以及适用的参数、返回值、异常、异步/线程、取消和副作用。无参数或无副作用可简述，不编造契约。
- 每个成员变量、属性和常量有中文用途说明；涉及时间、大小、坐标等写单位，涉及状态写语义、有效范围与生命周期。
- 重要局部变量、计算步骤和中间状态解释用途。简单循环下标和明显赋值不机械凑字数；核心算法、阈值、兼容分支解释原因、前提和边界。
- 新增或修改代码同步更新注释，发现错误注释必须修正。只覆盖本次范围，不批量整理无关历史代码；生成代码与第三方库排除且保持只读。
- 人工逐项核对：注释是否符合实际行为、单位/状态是否正确、错误和取消分支是否被说明、兼容原因是否仍成立。静态扫描只能发现候选缺失，不能自动证明中文语义准确；注释行数与覆盖比例不作为完成标准。
- 清晰命名、类型、测试和错误处理仍不可省略；TODO 写明原因与可验证的移除条件。

## 分级预算

- **D0/T0**：只检查注释和文档是否真实、无过期引用。
- **D1/T1**：对最终 Diff 做一次内联自检；不调用额外质量 Skill、不生成报告、不扩大到邻近历史代码。
- **D2/T2**：只对受影响文件检查职责、状态、错误、生命周期和必要注释。
- **D3/T3**：在方案阶段确认模块边界与真实变化轴，最终 Diff 再检查公共契约、依赖方向和复杂度。
- **D4/T4**：安全、数据完整性和发布证据优先；只改善本次改动中会增加风险的可读性问题，不借机重构。

机械格式、未使用符号和可确定的静态规则优先交给项目已有 formatter、linter、编译器或 LSP。不得为了执行本契约自动安装新工具。
