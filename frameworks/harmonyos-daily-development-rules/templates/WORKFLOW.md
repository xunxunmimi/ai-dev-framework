# HarmonyOS 日常开发工作流

适用于普通 HarmonyOS、ArkTS 和 ArkUI 开发。迁移项目、高风险发布流程和用户当前明确要求拥有更高优先级。

## 先定范围

先查看 Git 状态，保留已有修改。根据当前请求和实际影响选择等级；不因工程很大而自动提高等级。

先读 `.ai-project/lifecycle.json`。`migration-transition` 中普通鸿蒙 Bug、功能、构建和上线准备由本规则负责；只有迁移等价、缺失 iOS 行为或迁移证据任务才切换到 V2，单个任务不得同时使用两个主框架。`harmony-maintenance` 中 V2 仅作为历史资料。

测试反馈明确说“iOS 一致性”、“与苹果端流程不一致”或一次包含多项 iOS 差异时，属于 V2 迁移等价遗留，不按普通 D1 Bug 处理。明确“不涉及 iOS 一致性”时仍使用日常框架。

过渡期边界不清时运行 `.codex-rules/_shared/framework_router.py`；它只选择主框架，不读取业务文件或触发验证。

明确的 D0/D1 在内存中判断，不运行分类器、不写任务报告。范围不清、D2+、交接或工作区已有大量修改时，才使用 `.codex-rules/_shared/task_router.py` 保存任务基线并生成 `.ai-project/tasks/<task-id>/context.json`。分级采用 `pre → post → final`，最终只计算本任务文件，旧脏改动必须排除。

- **D0**：文档、注释、无行为变化的元数据。只做格式或解析检查；配置可能影响构建时才运行相应构建。
- **D1**：局部、可回退、影响明确的小 Bug。读取相关 `.ets` 文件和直接依赖，做最小修复；默认把应用运行验收交给用户。
- **D2**：一个页面、组件或普通功能，或涉及路由、持久化、异步状态和恢复的行为修改。检查相关状态，构建相关模块并按风险运行相关测试或冒烟流程。
- **D3**：跨模块、大功能、公共接口、数据模型或新依赖。先形成可审查方案，再分切片实现；验证受影响模块和关键集成路径。
- **D4**：账号、支付、权限、隐私数据、数据迁移、删除、签名或发布。记录风险和缺失证据，执行项目规定的完整验证；需要外部授权的操作停在授权前。

Codex 根据请求、改动范围和代码事实自行分级，用户无需声明大小。用户指定验证方式时遵从用户要求。不确定时从较小等级开始；只有依赖扩散、失败或不确定性得到证据支持时升级。修改行数少不一定是 D1；公共接口、数据、路由、权限或安全边界变化按实际风险升级。

## D0/D1 快速通道

- 默认不启动模拟器、不运行 UI 自动化、不截图、不录屏、不新增测试、不生成独立验收报告。
- 检查最终 Diff 和明显的 ArkTS 语法、类型、装饰器及资源引用问题。只有改动存在实际编译风险且有便宜的定向命令时才构建受影响模块。
- 不为了证明流程完整而调用 `ets-lsp-check` 或通用审查 Skill；`arkts-code-check` 只在改动确实涉及其合规风险时定向检查相关文件。
- 最终只简要说明改动、已做的最小检查，并标记“应用运行验收由用户完成”。
- 如果检查发现影响路由、共享状态、持久化、权限、生命周期或多个模块，自动升级到 D2/D3。
- 不读取历史迁移报告、原始日志、全量矩阵或无关模块；需要时只读取证据索引和局部条目。

## 外部能力自动路由

等级只控制调用上限；任务类型、项目配置和证据缺口共同决定是否调用。外部能力不可用不得阻塞普通开发，也不得在任务中自动安装。

### 蓝湖 MCP

- D0 默认关闭；只有用户明确要求从蓝湖整理需求时按指定文档读取。
- D1 仅限颜色、字体、间距、圆角、图标、切图等局部视觉问题，并且本次提供蓝湖链接或 `PROJECT.md` 已配置设计源；最多读取一个目标区域。
- D2 的 ArkUI 新页面、组件和视觉还原在设计源相关时读取目标页面总览、必要区域及素材。D3 只扩展到当前功能切片，不扫描整个蓝湖项目。
- D4 默认复用已有设计证据；只有发布阻塞明确来自视觉证据缺失时才读取。ArkTS 编译、类型、状态、路由、权限、数据和生命周期问题不调用。
- 默认只读，禁止自动发布、编辑、删除留言或发送通知。设计事实优先级按 `PROJECT.md` 执行；未配置时以当前应用行为和用户本次指令为准。

### Ponytail Review

- D0/D1 不自动调用。D2/D3 在实现和必要验证完成后，只有最终 Diff 出现一个强信号或两个普通信号时调用 `$ponytail-review` 一次；D4 默认不调用，除非用户明确要求。
- 强信号：新增依赖、单实现接口/工厂、重复实现平台能力、为局部功能新增完整中间层。
- 普通信号：多个无必要包装层、未使用扩展点、重复帮助函数、实现范围明显超出请求。
- 它只审查复杂度，不替代正确性、ArkTS 合规、安全、性能和发布验证；不得删除必要平台适配、生命周期处理、错误处理或可访问性支持。只采纳可证明不改变行为的建议，修改后重跑最小相关检查，不循环审查。

## 实施边界

- 先读取 `PROJECT.md` 中已填写的项目事实；未知内容从工程配置和源码确认，不猜测。
- D2+ 选择构建/测试时先读取 `.ai-project/detected-capabilities.json`，把它当候选索引而非授权；项目配置变化后定向刷新，未确认的 product、module 和 buildMode 不得猜测执行。
- 遵循现有模块、状态管理、路由、生命周期和依赖方式；不顺带重构无关代码。
- 使用 ArkTS 支持的语言能力，保持明确类型；不把普通 TypeScript 写法直接假设为 ArkTS 可用。
- 优先项目自带 `hvigorw`、SDK 和依赖配置；不自动全局安装工具、不切换依赖源。
- 编译错误、类型、装饰器或 Sendable 合规问题可使用 `arkts-code-check`。
- D2-D4 中明确需要 IDE/编译器级诊断且 ETS Language Server 可用时使用 `ets-lsp-check`；D0/D1 默认不使用。
- UI 修改检查布局、状态、路由返回、手势、键盘、窗口尺寸、字体缩放、深浅色及与任务相关的可访问性。
- 权限、后台任务、设备能力、支付和系统服务明确模拟器与真机证据边界。

## 代码质量与注释预算

- 所有源码改动都使用表达业务意图的命名、保持职责清楚，并让注释解释原因或约束而不是复述代码；修改后删除或同步失效注释。
- D0 只检查注释真实性。D1 只对最终 Diff 做一次内联自检，不调用额外质量 Skill、不生成报告、不整理邻近历史代码。
- D2 读取 `.codex-rules/_shared/references/code-quality-contract.md` 和 [references/code-quality-harmonyos.md](references/code-quality-harmonyos.md)，只检查受影响文件的状态、错误、生命周期和必要注释。
- D3 在方案和最终 Diff 两个阶段使用上述规则，检查模块边界、公共接口、依赖方向和真实扩展点。D4 仅用于本次高风险路径，安全与发布证据优先，不借机重构。
- 格式、未使用符号和确定性静态规则优先使用项目已有 formatter、linter、编译器或 LSP；不得为质量检查自动安装工具。

## 完成条件

运行对应等级的最小充分验证。D0/D1 允许把运行验收明确交给用户，不因此生成阻塞报告；D2-D4 不得把“代码已写”“能编译”或“页面能打开”单独当作功能正确。通过后，只有新失败、范围扩大或未解决风险才扩大检查。

选择或扩大验证时才读取 [references/verification.md](references/verification.md)。只报告实际运行过的证据，并区分新失败、既有失败和未验证范围。

## 身份、任务隔离与证据

按 `.codex-rules/_shared/references/task-control.md` 核对当前工程身份。小任务轻量只读确认；D2+、并行、脏目录或交接使用唯一任务 ID，独立 baseline/context/handoff，恢复核对真实文件。禁改 Pods 和其他第三方公共库，禁止 post_install/patch 间接修改，不创建候选工程。最终区分代码修改、编译、自动测试、真机待验、Git 提交及推送；仅报告已执行内容，未执行不推导成功。

## 中文注释验收

每个新增/改动的自有函数或方法中文说明用途与适用的参数、返回值、异常、异步/线程/取消和副作用；成员变量、属性、常量中文说明用途、单位和状态语义。重要局部变量、计算步骤、算法与兼容分支解释原因和边界；简单下标不机械注释。同步更新失效注释，生成代码及第三方排除。最终 Diff 人工核对语义准确性，不把静态通过或注释行数当质量证明。详细契约按本等级加载共享 code-quality-contract，D1 仍在内联自检完成，不生成额外报告。

## 读取授权与覆盖

先核对 read-policy 再读取项目事实；身份、快照、上下文和报告共用白名单。未知或受限路径不打开、不遍历；链接和读取错误阻塞。部分范围只执行 D0 配置核验，不运行无法限制读取的外部工具，未检查范围明确写入报告。策略变化使旧证据失效。详见共享 read-boundary.md。

## 约束来源和生效范围

区分用户长期项目规则、当前任务范围及平台具体拒绝。一次只读/配置接入不代表永久业务禁读，临时范围放入任务 read-policy 而不是共享项目策略。新对话不继承已关闭任务的范围。平台拒绝操作保留暂停，未给路径时不编造目录禁令；目录访问授权不能替代平台审批，也不得换名重试旧拒绝操作。

## 2.6 分级与预算补充

难度、范围、风险独立记录；全 App 视觉改动不能按单处颜色处理。支付/登录短句先做高风险定向排查，只有证据证明纯文案/颜色才降级；权限、签名、构建配置不能因 JSON 后缀归 D0。D4 只验证本次能力，真正发布或签名才选择对应 Release/最终包/适用真机，不机械全 App 构建。简单任务仍在内存分级，不增加角色/任务文件/报告，不全仓扫描；身份使用已确认事实和精确配置，不运行会全树扫描的探测作为仪式。并行仅在用户/适用规则允许且独立切片收益超过协调成本时采用。

## 鸿蒙项目迁移工作区不入库

所有鸿蒙项目（新迁移、迁移过渡期、日常维护）均将 `.migration-workspace/` 和 `.migration-workspace-v2/` 作为本地迁移工作数据，不提交、不推送、不放入源码交付包。它们可能包含仍在使用的计划、批准、状态、扫描缓存和测试证据，并非可直接删除的历史垃圾；不上传不等于删除。不得将 App 正常构建或运行所需的业务代码、资源、配置放入这些目录。

初始化项目、接入/升级规则或准备提交时，在项目读取/写入授权范围内检查 `.gitignore`，保留已有规则并补齐下面两行（无前导 `/`，同时覆盖根目录及子项目）：

```gitignore
.migration-workspace/
.migration-workspace-v2/
```

用 `git check-ignore --no-index` 检查实际候选路径，并检查 `git ls-files` 和暂存区；`.gitignore` 不会停止跟踪已入库文件，不得通过 `git add -f` 绕过。提交只暂存已审查的源码白名单，不将上述目录的新增/修改带入提交。发现已跟踪内容时报告范围，另行审查迁移验证脚本依赖及保留方案；未经专项授权，不执行批量 `git rm`、`git rm --cached`、删除本地目录或重写远端历史。

跨电脑继续迁移时，先检查本地所需状态/证据是否齐全；缺失时走授权的工作数据交接或可验证重建，不因 Git 克隆未包含它们而伪造完成记录。应用运行依赖与迁移验证依赖应分开说明。
