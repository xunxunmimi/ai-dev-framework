# Migration Frameworks 使用方法

## 1. 框架用途

`migration-frameworks` 用于把 iOS 项目迁移为 HarmonyOS ArkTS/ArkUI 项目。它追求“有证据的行为等价”，包括页面、状态、交互、接口、存储、权限、导航、生命周期、异常恢复、测试和视觉结果，而不是简单逐行翻译代码。

框架目录：

```text
<用户目录>/Desktop/MyProject/migration-frameworks/
```

其中有两个版本：

```text
migration-frameworks/
├── ios-to-harmony-migrator/
└── ios-to-harmony-dual-model-migrator/
```

## 2. 如何选择版本

### 单模型版

目录：`ios-to-harmony-migrator`

适合：

- 主要由 Codex 完成分析、架构、代码、测试和验收。
- 项目规模较小，或不需要让 Antigravity 单独承担 UI。
- 希望流程和责任边界尽可能简单。

### 双模型版

目录：`ios-to-harmony-dual-model-migrator`

适合：

- Codex 负责编排、架构、契约、业务逻辑、数据、平台能力、测试和最终验收。
- Antigravity 只负责工作单白名单内的 ArkUI 页面与纯视觉组件。
- UI 页面较多，希望通过串行交接减少 Codex 的视觉实现工作。

默认推荐双模型版，但两个模型不得同时修改同一迁移单元或同一工作树。

## 3. 使用前准备

准备以下内容：

- 可读取的 iOS 源项目，尽量保证可以构建和运行。
- 单独的 HarmonyOS 目标目录。
- Xcode、源项目依赖及必要的测试环境。
- DevEco Studio 和目标项目需要的 HarmonyOS SDK。
- 测试账号、接口环境、核心流程和产品要求。
- 尽可能完整的源应用截图和录屏。

重要边界：

- iOS 源项目只读，禁止格式化、移动或覆盖。
- 源项目和目标项目不能相同，也不能互相嵌套。
- 不要复制密钥、证书、Token、正式用户数据或生产环境私密配置。

## 4. 使用单模型版

运行：

```bash
python3 \
  "<用户目录>/Desktop/MyProject/migration-frameworks/ios-to-harmony-migrator/scripts/start_migration.py" \
  "/你的iOS源项目绝对路径" \
  "/你的HarmonyOS目标项目绝对路径"
```

示例：

```bash
python3 \
  "<用户目录>/Desktop/MyProject/migration-frameworks/ios-to-harmony-migrator/scripts/start_migration.py" \
  "<用户目录>/Desktop/Projects/MyIOSApp" \
  "<用户目录>/Desktop/Projects/MyHarmonyApp"
```

## 6. 初始化后生成的内容

目标项目中会生成：

```text
HarmonyOS目标项目/
├── AGENTS.md
├── .migration-agents/
│   ├── AGENTS.md
│   ├── project.json
│   ├── gate-config.json
│   ├── memory/
│   ├── matrices/
│   ├── rules/
│   └── evidence/
└── .migration-workspace/
    ├── migration-request.json
    ├── ir/
    ├── evidence/
    ├── reports/
    └── collaboration/       双模型版使用
```

- `.migration-agents/` 保存项目规则、路径、角色、矩阵、断点记忆和质量门禁。
- `.migration-workspace/` 保存源项目扫描、Migration IR、详细计划、批准记录、证据和报告。
- 双模型版使用 `collaboration/` 保存 UI 工作单、文件基线、交接、审查和当前 owner。

## 7. 第一阶段只能分析和制定计划

初始化后，AI 应先只读分析源项目并生成：

```text
.migration-workspace/ir/migration-ir.json
.migration-workspace/ir/migration-plan.md
.migration-workspace/ir/migration-plan.json
```

计划必须覆盖：

- 源项目结构、功能、依赖和平台能力。
- 迁移范围与明确不包含的内容。
- HarmonyOS 目标架构、模块和数据流。
- 分阶段迁移切片、依赖、目标文件和验收条件。
- UI、接口、数据、权限、存储、平台适配和测试。
- 风险、阻塞项、回滚方式和需要人工决定的问题。

计划生成后，AI 必须把计划摘要返回给你并停止。此时尚未开始业务代码迁移。

检查无误后明确回复：

```text
确认执行
```

没有这句明确确认，AI 不得开始迁移业务实现，也不得自行批准计划。

## 8. 批准计划

收到你的明确确认后，AI 才能记录批准：

```bash
python3 \
  "<用户目录>/Desktop/MyProject/migration-frameworks/ios-to-harmony-dual-model-migrator/scripts/plan_approval.py" \
  approve \
  "/你的HarmonyOS目标项目绝对路径/.migration-workspace" \
  --approved-by user
```

开始实施前检查批准仍然有效：

```bash
python3 \
  "<用户目录>/Desktop/MyProject/migration-frameworks/ios-to-harmony-dual-model-migrator/scripts/plan_approval.py" \
  check \
  "/你的HarmonyOS目标项目绝对路径/.migration-workspace"
```

单模型版使用相同命令结构，只需把路径中的 `ios-to-harmony-dual-model-migrator` 改为 `ios-to-harmony-migrator`。

批准凭证绑定 `migration-plan.md` 和 `migration-plan.json` 的内容哈希。计划修改后，旧批准自动失效，必须重新检查和确认。

## 9. 双模型协作流程

双模型版采用以下串行流程：

```text
Codex 定义计划、契约和 UI 工作单
→ Antigravity 认领 UI 工作单
→ Antigravity 只修改 editableFiles
→ Antigravity 提交交接
→ Codex 审查真实 Diff
→ Codex 接入业务逻辑
→ Codex 构建、测试、视觉和最终验证
```

查看当前状态：

```bash
python3 \
  "<用户目录>/Desktop/MyProject/migration-frameworks/ios-to-harmony-dual-model-migrator/scripts/collaboration_state.py" \
  status \
  "/你的HarmonyOS目标项目绝对路径/.migration-workspace"
```

状态中的 `owner` 决定下一位执行者。不能仅凭聊天约定所有权。

常见状态：

| 状态 | 下一位执行者 | 含义 |
|---|---|---|
| `ready_for_antigravity` | Antigravity | Codex 已发布 UI 工作单 |
| `antigravity_in_progress` | Antigravity | 正在编辑 UI 白名单文件 |
| `submitted_for_codex_review` | Codex | UI 已提交，等待审查 |
| `changes_requested` | Antigravity | 按审查意见返工 |
| `ui_accepted` | Codex | UI 通过，可接入逻辑 |
| `codex_integrating` | Codex | 正在接入逻辑和回归 |
| `verified` | 无 | 当前切片证据完整并通过 |

具体发布、认领、提交、审查和验证命令见：

- [`PROMPT_FOR_CODEX.md`](../migration-frameworks/ios-to-harmony-dual-model-migrator/PROMPT_FOR_CODEX.md)
- [`PROMPT_FOR_ANTIGRAVITY.md`](../migration-frameworks/ios-to-harmony-dual-model-migrator/PROMPT_FOR_ANTIGRAVITY.md)
- [`USER_GUIDE.md`](../migration-frameworks/ios-to-harmony-dual-model-migrator/USER_GUIDE.md)

## 10. 代码注释规则

两套迁移框架都包含迁移专用中文注释规则。核心要求：

- 公共契约、复杂状态机、并发与取消、生命周期映射、数据兼容、安全边界和非显然平台差异必须按适用范围注释。
- 注释解释原因、约束、风险和目标行为，不逐行翻译 ArkTS/ArkUI 代码。
- 迁移依据使用源仓库相对路径和稳定符号，禁止写本机绝对路径或粘贴大段 Swift/Objective-C 源码。
- TODO/FIXME 必须带稳定迁移 ID、原因和解除条件，并同步登记到迁移矩阵、阻塞项或决策记录。
- 禁止注释掉的旧代码、失败尝试、调试文本、AI 对话痕迹、无证据猜测和敏感信息。
- 行为变化时同步更新注释；删除实现时同步清理失效注释。过期或误导注释按代码缺陷处理。
- 注释不能代替 Migration IR、追踪矩阵、测试、人工计划批准和运行证据。

完整规则见：

- [单模型注释规范](../migration-frameworks/ios-to-harmony-migrator/references/commenting-rules.md)
- [双模型注释规范](../migration-frameworks/ios-to-harmony-dual-model-migrator/references/comment-rules.md)

## 11. 中断后恢复

使用完全相同的源项目和目标项目路径，再次运行原来的 `start_migration.py` 命令。框架会进入 `resume`，不会覆盖已完成的迁移成果。

恢复时 AI 必须读取：

1. 目标根 `AGENTS.md`。
2. `.migration-agents/AGENTS.md`。
3. `.migration-agents/memory/CURRENT.md`。
4. `.migration-agents/memory/INDEX.md`。
5. 当前覆盖矩阵。
6. 双模型版的 `.migration-workspace/collaboration/state.json`。
7. 当前 Git 状态和真实 Diff。

聊天记录不是迁移进度事实源。

## 12. 完成标准

以下条件没有满足时，不得宣称迁移完成：

- 迁移计划具有有效的人工计划批准。
- 必需功能均有源端证据、目标实现、测试和目标端证据。
- 构建、静态检查、单元测试、接口契约、关键 UI、数据和平台门禁通过。
- 源文件到目标文件的追踪关系完整。
- 真实账号、支付、权限、推送、硬件或后台能力按适用范围完成真机验证。
- 无法迁移或无法验证的内容已明确标记为 `blocked` 或 `unsupported`。

编译通过不等于行为等价，也不等于 100% 完成。
