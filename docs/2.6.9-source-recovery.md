# 2.6.9 精确框架源恢复

## 为什么会循环阻塞

任务运行会核对已安装规则及原始框架源。安装清单的 `suiteRoot` 指向可变 Git 检出时，源码变化会触发 `rules_identity`。取消命令也先经过 `protocol_gate`，因而无法取消；正常升级又要求无活动任务。单纯提高版本号无法解除这个循环。

## 支持的恢复路径

使用本版本 `installers/recover_source.py`。这不是升级，也不是完成任务。先从已知 Git 提交取得完整候选源码，再使用框架 pin 工具保存到独立固定目录，不能覆盖可变仓库或已有快照。

候选的版本号、完整 suite 摘要以及每个受管源文件摘要必须与原安装清单完全相等，项目内每个受管规则文件也必须未漂移。只有版本号相同不够。恢复过程不执行候选代码，不修改业务源码、任务状态、基线或证据，也不接受新的源码摘要。

默认只读预览。实际写入要求精确预览哈希、原因、确认人、授权来源及真实停写来源。检查 update→tasks 双锁、各任务验证锁，存在 pending execution 时拒绝。活动任务可保留原状，不需要为了恢复取消全部任务，也不能声称恢复等于验收通过。

只重绑定安装清单的 `suiteRoot`，另存审计记录。版本、suite 摘要、受管摘要、任务身份/基线/状态均不变。相同操作可重放，不重建任务；并发变化使预览失效。

```sh
python3 -B installers/recover_source.py /absolute/project \
  --candidate /absolute/pinned-original-source \
  --offline-writers-stopped '真实停写确认来源' \
  --reason '恢复原安装源码位置，不升级任务' \
  --confirmed-by '实际确认人' \
  --authorization-source '实际授权来源'
```

先审查预览。在完全相同的参数后添加 `--apply --expected-preview-sha256 <预览返回的完整哈希>` 才实际写入。参数文字不代替真实授权或停写核实。

## 恢复后继续工作

使用原固定框架和未变化的已安装规则继续原任务。后续如需升级，仍按正常 audit/update 流程及所有权/并发保护逐条核实任务状态，不批量伪造关闭。

历史 task-context 和 `.migration-v2/project.json.frameworkRoot` 可能仍指向旧可变检出；本窄恢复不重写这些项目事实。命令须明确使用恢复后的 manifest `suiteRoot`，不能继续从已变化的仓库运行旧任务。其他路径调整另行审查。

从固定源码运行 Python 命令使用 `python3 -B` 或 `PYTHONDONTWRITEBYTECODE=1`，防止导入时写入缓存。恢复拒绝未列入 pin 的文件、链接和特殊节点，不通过放宽检查接受被改动的快照。

## 必须停止的情况

找不到与原清单一致的完整源码、项目受管文件漂移、锁被持有、执行未释放或预览过期时，保留现场并说明缺失证据。不得改 manifest 哈希以接受新源、把新运行器复制进旧安装、删除状态或锁文件、编造完成或绕过活动任务检查。

## 验证范围

恢复专项测试覆盖 47 个活动任务保留、版本/摘要不符、源缺失、本地漂移、预览过期、锁冲突、pending execution 与重复请求；并运行原有升级、任务运行和代码交付回归。真实项目操作前必须验证候选固定快照，测试通过不代表所有真实项目已恢复。
